# Правила проекта для Claude

## Git

- **Всё делаем в `main`**: коммиты — прямо в `main`, отдельных веток не заводим (так решил владелец проекта).
- Коммитим, когда об этом просят; пушим — только когда просят отдельно.

## Общение

- **Кратко и тезисами**: каждый пункт — одна-две строки, без длинных абзацев.

## Зависимости

- **`electron-updater` не обновлять вслепую**: версия закреплена в пару к electron-builder (общий
  `builder-util-runtime`). После обновления — тест `update` (в том числе: докачка с GitHub по одному диапазону —
  на несколько сразу GitHub отвечает 501, и обновление качалось бы целиком, ~210 МБ) и запуск установленной сборки
  с обновлением на следующую версию.

## Тесты

- **Упал — сразу FAIL, не ждём таймаут.** Первой строкой каждого Electron-теста — `require('./_failfast');`:
  необработанная ошибка печатается как FAIL и завершает Electron. Новый тест без этой строки не пишем.
- `test/_isolated.js` (через него `run-all.js` запускает тесты) сам ловит тест, который не загрузился (синтаксическая
  ошибка — до `_failfast` дело не доходит): FAIL за секунду. Перед запуском нового или изменённого теста — `node --check test/<файл>.js`.
- Запускать тест с коротким внешним таймаутом и смотреть вывод; если тест висит — это баг теста (нет failfast,
  нет выхода по ошибке), а не повод ждать дольше.
- Ждать условие, а не фиксированную паузу: `settle(js, max)` (`test/_settle.js`) или опрос с ограничением времени.
- Скрытое окно не проигрывает CSS-анимации (меню и диалоги застывают прозрачными): в тестах со скриншотами
  выключать анимации стилем (`insertCSS('*, *::before, *::after { animation: none !important; transition: none !important; }')`).
- Исправление бага подтверждать тестом, который **падает без исправления** (проверить, временно убрав исправление).
  Для этой проверки гонять **только нужный сценарий** (отдельный короткий скрипт в scratchpad или один тест), а не весь
  длинный набор дважды подряд; ожидания в шагах — по условию и короткие (секунды, не десятки секунд).
- Внешние картинки и файлы Electron кэширует между запусками (общий профиль по умолчанию): тест загрузки внешнего
  ресурса — на свежем разделе (`partition`) или после `session.clearCache()`, иначе кэш скроет ошибку.
- Новый тест — в `test/run-all.js` (SUITE) и в таблицу тестов `docs/TECHNICAL.md`.
- Тесты улучшения картинки (upscale*) зависят от видеокарты — при переустановке драйвера их не запускать.
- Проверки скорости на настоящей видеокарте (апскейл успевает, плавность) — только когда её не занимает другое
  приложение (игра): иначе честное «не успевает» выглядит как провал, и падают каждый раз разные сценарии. Перед
  замером — загрузка по `nvidia-smi`; занята — `SKIP [...] причина` (run-all покажет пропуски в итоге), а не FAIL и не
  ослабленный порог. «Падает, но по-разному от запуска к запуску» — сначала посмотреть, кто ещё грузит видеокарту.
- После правки модулей `public/js` — проверка синтаксиса до запуска тестов: копия файла с расширением `.mjs` и
  `node --check` (синтаксическая ошибка в модуле роняет все экраны, которые его импортируют).
- Тест сообщает о провале так, чтобы `run-all` это увидел: ненулевой код выхода или `FAIL` в выводе. Свой формат
  отчёта (как `LOW-CONTRAST:` у `contrast.js`) — только вместе с правилом в `FAILED` в `run-all.js`; новый тест
  один раз прогнать через `node test/run-all.js <тест>` с заведомо плохим результатом.
- Синтетическая разметка может не воспроизвести баг: тест строить на настоящем сценарии (настоящий экран, окно
  нужного размера), и проверка «падает без исправления» обязательна — без неё уже был тест, который ничего не ловил.
- Ждать настоящий контент, а не скелетон: у строк скелетона те же классы (`.comment`, `.release-row`), тест, который
  «нашёл» скелетон, проверяет пустоту и проходит на сломанном коде. Отбирать `!el.closest('.skeleton, .sk-root')`.
- Задержка сети в тесте — точная: подменять ответ заранее полученным (своя сеть добавляет 200–400 мс, и «быстрый»
  ответ оказывается медленным). Видимость — с учётом родителей (кусочки скелетона непрозрачны, прячется `.sk-root`).
- Тема системы в тестах — явно (`nativeTheme.themeSource`): иначе результат зависит от темы Windows на машине.
- Скриншоты и CSS-анимации в тестах — окно `offscreen: true`: в показанном окне `capturePage` падает
  (`UnknownVizError`, окно перекрыто), в скрытом не идут CSS-анимации.

## Android (`android/`, docs/TECHNICAL.md → «Android»)

- Отличия платформ — флаги `public/js/platform.js` (`ANDROID`, `has.*`, `touch`), а не проверки `window.anixartNative`
  (на Android он тоже есть — shim.js). Стили только для телефона — `android/web/android.css`.
- Тесты: `node android/test/run-all.mjs` (эмулятор `Anix_Test` без PIN-кода). Новый тест — в SUITE `run-all.mjs` и в
  таблицу docs/TECHNICAL.md. Нажатия — `tap()` (палец по координатам), не `el.click()`.
- `until()` ждёт **строку-выражение страницы**; условие на стороне теста — `waitFor()` (функция в `until` — всегда
  «истина», так уже были пустые проверки). В JS для страницы внутри шаблонной строки — `\\s`, `\\.` (иначе `\s` → `s`).
- localStorage WebView пишет на диск с задержкой ~1 с: перед перезапуском — `persist()` (свернуть и подождать).
- Android 17 не пускает приложение в локальную сеть (10.0.2.2): тестовый сервер на компьютере — через `adb reverse`.
- Системные окна эмулятора (подсказка «Viewing full screen», ввод стилусом Gboard) забирают касания — их гасит
  `ensureDevice()`; «тап не дошёл» — сначала скриншот, что сверху.

## Повторяющиеся ошибки

- **Правило для «всех шапок/экранов» — проверять на всех настоящих экранах**, а не на подставленной разметке одного:
  разделитель перед кнопками окна «только если справа есть кнопки» проверили подменой шапки — а почти у каждой шапки
  `backToolbar` справа скрытая «Смотреть вместе» (`.only-in-room`), и правило не сработало ни на одном экране.
  Список экранов — как в `test/transitions-audit.js` (`test/titlebar.js` проходит их все). Видимость — по
  `getClientRects()`, а не по наличию элемента.

Когда пользователь указывает на ошибку, которая повторяет уже сделанную (или того же рода), — исправить и сразу
дописать сюда правило: что случилось и как не допустить. Перед работой над интерфейсом и анимациями — перечитать.

- **Просят сделать конкретным инструментом/скиллом — работать по его процессу**, а не брать его как справочник.
  Если отступаешь от процесса — сказать об этом до работы, а не после. (Анимации сначала сделали своим
  скриптом вместо скилла text-to-lottie.)
- **Анимации Lottie (`js/lottie.js`, сцены — `tools/lottie-studio`, правка сцены → `node tools/lottie-studio/sync.mjs`):**
  - то, что видно до готовности анимации, совпадает с её начальным кадром: иконка в покое — статичная иконка;
    начальный кадр пустой (вступление из пустоты) — `blank`; начальный кадр приглушённый — `muted`. Иначе
    мелькает статичная иконка, потом пропадает, потом анимация (звёзды оценки, пустые экраны, галочка тоста);
  - несколько анимаций по очереди — запускать, когда готовы все (`el.ready`), а не по таймеру от клика;
  - цвет: смена цвета кнопки не должна перекрашивать середину анимации (снятие сердца мелькало тёмным) —
    `heartIcon.set()` до смены цвета кнопки;
  - вынутая из DOM анимация оставляет снимок кадра — возврат на экран без пустого места;
  - lottie-web считает `currentFrame` и `goToAndStop` от начала последнего проигранного отрезка: перед переходом
    в кадр покоя — `resetSegments(true)` (`stopAt` в lottie.js), в тестах — абсолютный кадр (`currentFrame + firstFrame`);
  - разовые отклики (нажали, сменилось число/статус) — `nudge`/`rollTo`/`flySend` из ui.js, полосы — `growBars`;
  - сцена иконки, у которой меняется форма, — Lottie; если иконка только сдвигается/пружинит — `nudge` (без файла
    и заглушек). Кадр покоя сцены = статичная иконка Material (та же геометрия): сверять картинкой — рядом, в таком же
    контейнере (кнопке) и того же цвета (иначе сравнение ловит цвет, а не форму; `test/lottie-icons.js`);
  - жест при наведении на кнопку действия — `actionIcon`/`iconButton` (ui.js) → `hoverIcon` (lottie.js), иконки в
    строках списков (история поиска и т. п.) — статичные: это не действия.
- **Браузер перезапускает CSS-анимации при каждой вставке в DOM** (возврат на вкладку, пересборка шапки):
  разовый эффект «пришло новое» (бейдж выпрыгивает, колокольчик звенит) — из JS и только при изменении состояния.
- **`backdrop-filter` под экраном с анимацией прозрачности** (въезд экрана) после конца анимации меняет цвет —
  на экранах с въездом его не ставить (шапка релиза темнела «раз в 5 заходов»).
- **`overscroll-behavior: contain` на вложенном списке без переполнения глушит колесо** — родитель не листается;
  ставить только при переполнении: `containScroll()` из `ui.js` (чат комнаты).
- **Пустой экран, ошибка, «не найдено» — по центру всего экрана, чуть выше середины** (оптический центр), а не по
  центру места под шапкой — под высокой шапкой так смотрится ниже середины окна. `.empty` растягивается (app.css),
  отступ считает `centerEmpties` (ui.js). Заглушку не ставить в обёртку, которая ломает цепочку растяжения;
  если под заглушкой идёт контент — `.empty.inline`. «Отцентровать» — проверять глазами на нескольких экранах
  с разной высотой шапки, а не одной формулой.
  Одинаковые ситуации — одинаковая заглушка (`emptyView`/`errorView`), а не своя разметка с другой иконкой.
- **Одно и то же аниме в разных местах — разные объекты**: смена статуса/избранного на странице аниме обновляет
  списки через `releaseChanged()` (common.js); новый вид релиза со статусом или сердцем — регистрировать (`trackRelease`).
- **Комментарии**: ответы — в ветке под комментарием (`commentItem`), не на отдельном экране; поле — `commentComposer`
  (одна плашка, «Спойлер» — значок-переключатель), без строки «Ответ: …».
- **Действие меняет данные — экран обновляется сам** (удалили/изменили комментарий, сменили статус): колбэк, который
  никто не передаёт (`onChanged` у меню комментария), — та же ошибка; обновление — внутри самого компонента.
- **Кеш данных** (память недавно открытых релизов и `remembered()` для экранов, api.js; `pagedList({ remember })` —
  первая страница списка): показ из памяти — всегда с фоновым обновлением
  (изменилось видимое — экран обновляется сам), очистка при смене аккаунта (`auth-changed`) и защита от ответов,
  запрошенных до неё (`releaseGen`). Новый кеш с личными полями — так же.
- **Свежие данные на показанном экране — точечно и плавно, не пересборкой**: пересборка сбрасывает открытые ветки,
  начатый текст, заново растит полосы и пересоздаёт анимации. Страница аниме — `livePatch` (только изменившиеся
  блоки), профиль/коллекция/списки — `morph` (ui.js: новое дерево из того же объекта данных вливается в показанное;
  числа перекатываются, полосы доезжают; `.lt`, `.paged`, `[data-keep]` не трогаются; пункты списков — по `data-key`).
- **Переход — одна анимация**: въезд экрана (router.js → ui.js `enterScreen`, Web Animations по уже вставленным
  блокам) двигает и проявляет контент под шапкой; шапка (.appbar) сразу на месте. Контент, сменивший скелетон, во
  время въезда подхватывает его с того же места (`joinEnter`), после въезда — встаёт сразу, без своей анимации.
  Своё проявление контента (`swapIn`, CSS content-in) после въезда — это вторая анимация, пользователь видит её
  как «снова анимация». CSS-класс въезда не годится: цепляется к блокам, вставленным позже.
  Убирая вторую анимацию, искать **все** CSS-анимации на вложенных блоках (`grep animation: app.css`), а не одну:
  `.tabbody > *` проявлялся с нуля поверх въезда — блик на «Списках просмотра» (экран со вкладками). Проявление
  вкладки — только при переключении пользователем (`tabs` в ui.js, разово через `nudge`).
  Шапка — это всё, что прилипает сверху: `.appbar` **и** полоса вкладок `.tabbar` (не `.static`); въезд их не
  трогает (`enterParts` в ui.js). Подхват въезда — с тем же `startTime`, что у въезда (currentTime у новой анимации
  фиксируется только к следующему кадру — блок отставал на 1–3 кадра).
- **Чинишь переход на одном экране — прогони все**: `test/transitions-audit.js` покадрово проходит все экраны
  (вкладки, вперёд, назад, из памяти, вкладки внутри экрана). Новый экран — добавить в его список. Жалобы «мигает и
  здесь» шли по одной, потому что проверяли только экран из жалобы.
- **Переход без голого экрана**: данные не успели за ожидание перехода — скелетон въезжает вместе с экраном.
  Загрузку начинать как можно раньше (страница аниме — с нажатия кнопки мыши на месте, `prefetchRelease(id, { now: true })`;
  экраны со списком — `prefetchRead(ключ, загрузка)` с `pointerdown` кнопки и тот же ключ в `pagedList({ remember })`:
  «Комментарии», уведомления). «Данные приходят почти сразу, а скелетон мелькает» — значит, ответ медленнее ожидания
  перехода (100 мс): либо грузить с нажатия, либо из памяти (вкладки, которые пересобираются при выборе, — тоже).
  Менять поведение загрузки — снимать кадры при ответе за 150/250/600 мс до и после и сравнивать глазами.
- **Скелетон — из тех же классов, что и контент** (`.card`, `.info-rows`, `.screens`, `.watch-row`…), с серыми
  заглушками внутри: размеры и переносы совпадают сами. Секции — все обычные, до низа страницы (не пустота
  под первой карточкой). Сверять скелетон с настоящей страницей рядом, на всю высоту и на узкой ширине.
  Есть данные строки списка (`preload`) — в предпросмотре настоящий текст из них (строки сведений, описание), а не
  серые полоски: совпадает до пикселя. Серые полоски — высотой строки текста (21 px, не 20), описание — те же
  свёрнутые строки `.desc-text`. Мерить по частям (строки, описание, кнопка), а не допуском «±15% высоты» —
  такой допуск пропускал заметное несовпадение.
- **Кнопки шапки — с первого кадра загрузки**: шапку не пересобирать после загрузки данных, иначе кнопки
  появляются позже и сдвигают соседние (страница релиза).
- **Меняешь общий класс — проверь всех, кто им пользуется** (`grep` по классу в js): `.comment-input` переделали
  под поле комментария, а поле чата ИИ с тем же классом развалилось — кнопка уехала под поле.
- **Воспроизводить ровно тот путь, которым пользуется пользователь**, прежде чем говорить «исправлено»: страницу
  аниме открывают кликом по строке списка — с предпросмотром из её данных (`preload`), а не `navigate` без них.
  Мигание шапки из предпросмотра «исправленным» объявили по съёмке другого пути.
- **Проверка анимации/перехода — покадрово в самом приложении**, в обеих темах: первый показ, конец анимации,
  возврат на экран через >4 с, режим экономии. Отдельный плеер или песочница не заменяют настоящий экран.
